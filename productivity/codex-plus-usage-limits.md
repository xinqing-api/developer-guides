# Codex + ChatGPT Plus 使用额度说明：5 小时窗口、模型选择与省额度实践

> 适用对象：使用 ChatGPT Plus 运行 Codex 本地任务的开发者。
> 数据核对日期：2026-08-16。额度与产品规则可能调整，请以文末官方页面为准。

很多人会问：“Plus 每个月到底有多少 Token？”这个问题放在 Codex 上并不准确。

Codex Plus 不是一个每月发放固定 Token 的账户。你能完成多少任务，取决于模型、上下文、推理强度、工具调用、检索、缓存，以及任务在本地还是云端运行。两条看起来相似的消息，实际消耗可能相差很大。

本文解决五个问题：

1. Plus 的 5 小时窗口如何理解；
2. Sol、Terra、Luna 大约能使用多少次；
3. 哪些任务最容易消耗额度；
4. 如何为任务选择合适的模型；
5. 如何设计更省额度的 Codex 工作流。

## 1. 先建立正确的额度模型

不要把 Codex 用量理解成：

```text
每月固定 Token - 每条提示词长度 = 剩余额度
```

更接近真实情况的简化模型是：

```text
任务消耗 ≈ 模型系数
         × 有效上下文规模
         × 推理与迭代深度
         × 工具、检索和执行成本
         × 速度模式系数
         - 缓存收益
```

这不是 OpenAI 公布的计费公式，而是帮助工程决策的心智模型。官方明确说明，模型选择、上下文、推理、工具使用、检索和缓存都会影响用量，因此提示词长度本身不是可靠估算依据。

### 消息数为什么不是固定次数

比较下面两个任务：

**任务 A**

```text
把 src/config.ts 中的超时时间从 10 秒改成 15 秒，并运行对应单测。
```

**任务 B**

```text
分析整个仓库的超时问题，重构网络层，修复所有潜在缺陷并验证。
```

它们都只发送一条消息，但任务 B 可能需要扫描更多文件、持有更长上下文、制定计划、执行命令、处理失败并重复验证。实际消耗自然不会相同。

## 2. 什么是滚动 5 小时窗口

Plus 的本地消息与相关 Agent 能力共享滚动 5 小时窗口，并且可能存在额外的每周限制。

“滚动”意味着系统持续统计最近 5 小时的使用，而不是每天凌晨统一重置。早期用量逐步离开窗口后，可用空间也会逐步恢复。

```mermaid
timeline
    title 滚动 5 小时窗口示意
    09:00 : 开始使用
    10:30 : 运行一批重任务
    12:00 : 剩余额度下降
    14:00 : 09:00 附近的用量开始移出窗口
    15:30 : 10:30 附近的用量逐步释放
```

需要注意：5 小时窗口恢复，不等于所有限制同时清零。若账户同时触及周限制，仍需等待对应周期恢复或使用账户提供的额外额度选项。

## 3. Plus 本地消息的官方估算区间

截至 2026-08-16，OpenAI 官方 Codex 定价页面给出的 Plus 本地消息估算如下：

| 模型 | 每 5 小时本地消息估算 | 推荐角色 | 典型任务 |
|---|---:|---|---|
| GPT-5.6 Sol | 10–100 | 攻坚 | 复杂架构、疑难调试、模糊问题、高风险判断 |
| GPT-5.6 Terra | 25–200 | 日常主力 | 功能开发、代码审查、文档分析、报告与常规重构 |
| GPT-5.6 Luna | 250–2,000 | 轻量跑量 | 分类、抽取、格式转换、批处理与边界清晰的小任务 |

这些是估算区间，不是保证的固定次数。区间越宽，越说明任务规模和使用方式会显著影响结果。

## 4. 如何选择 Sol、Terra 和 Luna

一个实用原则是：**按任务难度分层，而不是默认选择最强模型。**

### Luna：先做便宜的确定性工作

适合：

- 文件分类和信息抽取；
- 批量改名、格式整理和机械修改；
- 日志初筛与问题归类；
- 边界清晰、验收标准明确的小型编码任务；
- 后台自动化和高频支持任务。

避免把需要跨模块权衡、复杂推理或高风险决策的任务直接交给 Luna。

### Terra：承担大部分日常生产

适合：

- 常规功能开发；
- 有明确范围的 Bug 修复；
- 报告、文档和代码分析；
- 中等规模重构；
- 需要可靠判断、但不属于最难问题的工作。

对多数专业用户，Terra 应该是默认主力，而不是 Sol。

### Sol：只处理真正困难的部分

适合：

- 架构设计与重大技术决策；
- 难以复现的复杂故障；
- 跨模块、跨系统的深度推理；
- 安全敏感或高风险改动；
- 需求模糊、需要主动澄清和规划的任务。

简单决策树：

```text
任务是否边界清晰、可机械验收？
├─ 是 → Luna
└─ 否 → 是否属于常规生产工作？
        ├─ 是 → Terra
        └─ 否 → Sol
```

## 5. 哪些行为最容易消耗额度

### 5.1 长会话携带大量无关上下文

旧需求、已解决的报错和无关文件持续留在同一会话中，会让后续任务背负越来越重的上下文。

**改进：**新问题开启新会话，只提供当前任务必需的信息。

### 5.2 反复扫描整个大型仓库

“再完整检查一遍”可能触发重复文件读取、检索和分析。

**改进：**先让 Codex 列出需要检查的目录和文件，确认范围后一次性执行。

### 5.3 任务没有边界

“优化整个项目”没有明确终点，Agent 会持续扩展范围。

**改进：**定义目标、允许修改的路径、禁止修改的区域和验收命令。

```text
目标：修复登录接口的超时问题
范围：src/auth/**、tests/auth/**
禁止：不修改数据库结构和公开 API
验收：npm test -- auth && npm run lint
```

### 5.4 不断试错，却没有先制定计划

在没有定位根因时连续修改代码，容易产生大量无效工具调用和回滚。

**改进：**先要求“只诊断并给出证据”，确认原因后再授权修改。

### 5.5 使用更高速度或高消耗媒体能力

官方说明指出，Fast 模式会更快消耗适用模型的额度；图片生成平均会以约 3–5 倍速度消耗包含额度，实际取决于图像质量和尺寸。

## 6. 一套更省额度的三阶段工作流

### 阶段一：Luna 做整理与缩小范围

```text
读取错误日志并完成三件事：
1. 按根因类别归组；
2. 标出最可能相关的文件；
3. 输出不超过 10 行的调查清单。
不要修改代码。
```

目标是把大量原始材料压缩成清晰问题。

### 阶段二：Terra 完成主要实现

```text
根据调查清单修复问题。
只修改列出的文件；先给出计划，再实施；
运行相关测试并总结改动与验证结果。
```

大多数日常开发工作可以在这一阶段结束。

### 阶段三：Sol 解决剩余难点

```text
当前实现仍在并发场景下失败。
请分析竞态条件，比较至少两种修复方案，
说明风险后实施最稳妥方案，并补充回归测试。
```

把 Sol 留给真正需要深度推理的 20%，通常比全程使用 Sol 更有效率。

## 7. 发布任务前的省额度检查表

- [ ] 目标是否只有一个？
- [ ] 是否写明允许修改的路径？
- [ ] 是否写明禁止修改的区域？
- [ ] 是否提供最小必要报错和文件？
- [ ] 是否可以先用 Luna 做整理？
- [ ] Terra 是否足以完成主体任务？
- [ ] Sol 是否只处理真正的难点？
- [ ] 是否有明确的测试或验收命令？
- [ ] 是否避免重复扫描整个仓库？
- [ ] 新问题是否应该开启新会话？

## 8. 常见问题

### Plus 是否包含 API 额度？

不包含。ChatGPT Plus 与 OpenAI API 是不同的计费体系，API 调用仍需单独付费。

### 为什么我没有达到表格上限？

表格是估算区间。大型项目、长上下文、复杂推理、工具调用和重复迭代都会提高单条消息消耗。

### 5 小时后额度一定全部恢复吗？

不一定。窗口是滚动恢复，并且可能存在额外的周限制。

### 是否应该永远使用 Luna？

不是。选错模型可能导致反复失败和更多重试，反而浪费额度。应选择能够稳定完成任务的最轻模型。

## 结论

Codex Plus 的使用效率，主要取决于三个选择：

1. 是否控制上下文和任务范围；
2. 是否让 Luna、Terra、Sol 各自承担合适角色；
3. 是否先诊断和规划，再集中执行与验证。

记住一句话：**Luna 能做就不用 Terra，Terra 能做就不动 Sol；但不要为了省额度，让轻量模型反复失败。**
